# Этап B.2 — мастер-источник для финальных экспортов (отчёт)

Дата: 2026-10-23. Ветка: `quality-max`. Коммит: B.2 (локальный).

## Что сделано

Добавлен «мастер-источник» — запись пути к последнему до-деливерному потоку с
полным набором эффектов (транс/поворот, отражение, автозум, визуальные слои,
субтитры, глушение аудио) в состояние задания. Подготовка Instagram/YouTube/Telegram
читает мастер вместо `final.mp4` (когда он доступен и пригоден), алгоритмы
подготовки (B.3) не тронуты.

Архитектура выбрана по результатам бенчмарка форматов (см. ниже): вместо создания
отдельного `master.mp4` лишним транскодированием (что запрещено требованием «не
добавлять лишние проходы») мастер — готовый промежуточный файл, путь которого
записывается в `job_state.json` (режим по умолчанию `inplace`, 0 байт дополнительного
места). Опциональный режим `copy` создаёт побитово-точную копию `master.mp4`;
режим `none` возвращает прежнее поведение (мастер не записывается).

## Бенчмарк форматов мастера (первым шагом, до выбора)

Вход: `sub_words.mp4` из ранее сделанного продакшен-рендера B.1 (`/tmp/b1_qa2`,
720x1280, 218 кадров, intermediate crf 0 yuv420p), 7.27 с.

| вариант | проходов | время | размер | точность vs поток |
|---|---|---|---|---|
| stream-copy / inplace | 0 / 0 | 1.4 с (копия) / 0 с | 70 923 КБ / 0 КБ (уже есть) | побитово идентично |
| H.264 CRF 0 yuv444p | 1 | 7.0 с | 85 716 КБ (+21 %) | в 444-пространстве математически lossless (PSNR inf), при обратном сведении к 420 — не бит-точно |
| FFV1 | 1 | 2.4 с | 67 MB (avi) / 113 MB (mkv) | НЕ mp4-совместимо (нет тега в mp4): при декоде из avi/mkv — расхождение кадров/таймстемпов, PSNR ~26 дБ (артефакт синхронизации), рассинхронизация |
| ProRes 422 HQ | 1 | 3.8 с | 97 727 КБ (+38 %) | PSNR 55.5 дБ (потеря ощутима измеримо) |

Диск реально находится на 86 % занятости (~28 ГБ свободно) — постоянные копия/перефор
мат мастера на каждое задание давят на место без выигрыша качества: качества
inplace-файла «потолок»-посредника (все эффекты уже в нём), а FFV1/ProRes — это
большая скорость/размер за то же самое содержимое или измеримую потерю.

**Вывод**: мастер = inplace-указатель на уже созданный поток (0 лишних проходов,
бит-точность, 0 дополнительного диска); `copy` и `none` — опции, бенчмарк сохранён
в `/tmp/b2_master_bench` (в репозиторий не входит).

## Реализация

`montage/engine.py`:
- после этапа глушения аудио (и до деливерного кодирования) выбирается мастер-файл:
  при глушении — `censored_audio.mp4` (видеопоток там — битовая копия `sub_words`,
  заменён только звук), иначе `sub_{режим}.mp4` / поток без субтитров;
- env `AUTOMONTAGE_MASTER_MODE` = `inplace` (по умолчанию) | `copy` | `none`;
  неизвестное значение → сообщение + откат к `inplace`;
- `copy` создаёт `master.mp4` побитовой копией (`shutil.copy2`) с проверкой
  свободного места (нужно размер файла + 64 МБ); нехватка/ошибка → откат к `inplace`
  с сообщением;
- в `meta` добавлены поля `master_video` (имя файла в каталоге задания) и
  `master_mode`; кодирование final/preview и параметры — без изменений.

`app.py`:
- `_master_video_path` — разрешает записанный путь (устаревние/старые задания без
  поля → None → прежнее поведение);
- `_prep_source_video` (не-зеркальный вариант) теперь сначала пробует мастер;  непригодный файл (ffprobe: нет видео-потока) → откат к `result_video` с warning
  `[montage-prep] ... master unreadable`;
- `_protected_montage_paths` защищает мастер от `cleanup` пока задание НЕ в
  завершённом состоянии публикации (`stage=published` и без `publish_errors`);
  после успешной публикации мастер удаляется проверенным пайплайном
  `_cleanup_publish_artifacts` (управляемая политика хранения, без бесконечного
  накопления);
- при ошибках публикации публикация-клинап целиком пропускается (существующее
  поведение, мастер сохраняется для повторной попытки);
- кеш подготовленных вариантов (`publish_prep`) инвалидируется автоматически:
  подпись строится от идентификатора файла источника (путь/размер/mtime) — смена
  источника с `final.mp4` на мастер или перерендер (новый файл мастера)
  делает старые записи несвежими (без повторного использования);
- отражённый вариант — отдельный рендер, читает sourcе-видео; на мастер не влияет.

Сценарий «рендер завершён → перезапуск приложения → поздняя подготовка»:
состояние задания (включая `result.master_video`) пишется в `job_state.json`
(`_save_montage_job`), при рестарте `_recover_montage_jobs()` восстанавливает его
из диска; мастер-файл физически не удаляется клинапом (защита), поэтому поздняя
подготовка (Instagram/YouTube/Telegram) работает с ним как до, так и после
перезапуска. Покрыто новыми тестами.

## Сравнение с B.1 (продакшен-рендер на тех же входах)

Полный продакшен-сценарий: тот же источник (`montage_work/9a7cf622/project_video.MOV`),
тот же SRT (слова), zoom timeline + subtitles(words), diagnostic ON:
`/tmp/b2_master_e2e/b2prod`.

| параметр | B.1 (`/tmp/b1_qa2/p420b`) | B.2 | дельта |
|---|---|---|---|
| encode-проходов (не counting master) | 5 (rotate, zoom, subtitles, finalize_hevc, preview_h264) | 5 (те же; PASS_COUNT подтвержден) | 0 |
| лишние транскоды ради мастера | — | 0 (inplace) | — |
| время движка (диагност. прогон) | ~43 с (app-уровень B.1) | 35.2 с (движок) | сравнение условное: разные точки измерения |
| final.mp4 | 10 343 КБ | 10 106 КБ | ~0–2 % (разброс между рендерами; параметры кодирования те же) |
| preview.mp4 | 18 846 КБ | 18 783 КБ | ~0–2 % |
| sub_words.mp4 (мастер) | 70 923 КБ | 72 888 КБ | ~2–3 % (в B.2-прогоне другой набор опций субтитров: главное — одинаковое число проходов и параметры кодирования) |
| пик диска | как в B.1 | тот же + 0 КБ (мастер — уже существующий файл) | — |

PSNR/VMAF геометрии зум/субтитры в B.2-этапе не пересчитывались (параметры
этапов не менялись — изменение качества между B.1 и B.2 исключено по построению;
QA-фаза сверит полные метрики против артефактов B.1).

## Тесты

Полный suite: `python3.9 -m unittest discover -p "test_*.py"` — **195 тестов OK**
(189 из B.1 + 4 новых в `test_montage_cleanup.py` + 2 новых
`test_montage_master_restart.py` производят 6 дополнительных проверок).

Новые test-кейсы:
- разрешение пути мастера + фоллбэки (нет файла, устаревшие задания без поля,
  copy-режим, имя == result_video);
- маршрутизация подготовки через мастер + откат потерянного/повреждённого;
- render-cleanup не трогает мастер незавершённого задания;
- publish-cleanup удаляет мастер после успешной публикации и пропускает всю
  очистку при ошибке публикации (мастер сохраняется для повторной попытки);
- скрипт рестарта: `_recover_montage_jobs()` восстанавливает задание, поздняя
  `_prep_source_video` читает мастер, cleanup его сохраняет; при отсутствии
  мастера — откат к `result_video` без падения.

## Ограничения / заметки для QA

1. PSNR-сравнение `sub_words.mp4` B.1 vs B.2 (19.6 дБ) — ожидаемо: в B.2 прогоне
   другие опции субтитров (без выделения слов и других фич QA-прогона B.1);
   сравнение параметров/проходов — главное.
2. `copy`-режим мастера — протестирован юнит-образно (путь/защита/клинап);
   полный продакшен-рендер с `AUTOMONTAGE_MASTER_MODE=copy` в QA-фазе.
3. Master хранится in-place до успешной публикации — промежуточные `sub_*.mp4`
   (+73 МБ на типовое 7-сек задание) живут дольше, чем раньше (только до
   публикации); disk-impact в норме, но для 20+ паралл заданий стоит мониторить
   занятость диска (QA-фаза).
4. Политика: после успешно опубликованного задания готовые prepared-файлы
   Instagram/YT/TG уже лежат платформенно, мастер удаляется; повторная
   подготовка с нуля после публикации — работает с `result_video` (fallback).
